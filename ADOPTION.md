# Внедрение и ревью

[Спецификация](SPECIFICATION.md) — источник правил. Этот документ помогает применить их в существующем или новом проекте.

## Порядок внедрения

1. Зафиксировать совместимую версию TanStack Query v5 и включить строгую проверку TypeScript.
2. Выбрать один ресурс. Зафиксировать его параметры, форму ответа, текущие ключи, consumer и мутации, влияющие на кэш.
3. Отделить transport от кэширования. Transport получает аргументы и `AbortSignal`, возвращает типизированные данные или ошибку.
4. Перенести идентичность ресурса в `.qk`, сохраняя действующие ключи при миграции. Смена ключа — отдельное изменение поведения кэша.
5. Описать чтение самостоятельными QO. Перенести технические guards в `skipToken`, оставив решения об активности у consumers.
6. Описать запись самостоятельными MO и перенести туда все связанные изменения кэша.
7. Подключить типизацию meta и универсальный invalidation executor, если MO используют `meta.invalidates`.
8. Заменить consumer-код на прямое использование options. Вынести композицию QO/MO и специфичные для сценария мапперы и бизнес-guards в Aggregation при необходимости; повторное использование в других сценариях не обязательно.
9. Проверить UI, загрузчики, предзагрузку и SSR на одинаковую идентичность ресурса.

Правила применяются к новому коду и существенно изменяемым модулям. Массовая миграция не обязательна. Совместимость со старыми ключами и persisted cache оценивается до их изменения. Переход от позиционного ID к `{ productId }` меняет идентичность записи кэша: все QO и cache-effects MO одной операции переводятся согласованно; для persisted cache нужно определить миграцию или сброс старых записей.

## Вопросы для ревью

| Область | Что проверить |
| --- | --- |
| Зависимости | Consumer не импортирует QK, transport не зависит от Kit |
| Ключи | Все влияющие параметры учтены, readonly tuples, именованные объекты параметров, готовые обязательные ID, разные ветки для finite/infinite |
| QO | Отдельные экспорты, signal передан, технические guards до конкретного QK, отдельный unavailable-ключ + skipToken при отсутствии ID, нет enabled и overrides-аргумента |
| Параметры | QK/QO/MO принимают один именованный объект или не имеют параметров; variables mutationFn — объект |
| Типы | Inference сохраняется через options и select; нет `any` или casts, скрывающих ошибку контракта |
| MO | Все cache-effects внутри MO, callbacks не перезаписаны consumer, Promise ожидается |
| Meta | Тип зарегистрирован и executor действительно установлен на используемом клиенте |
| Aggregation | Только ссылки на QO/MO и чистые функции; нет hooks, keys и side effects |
| Consumer | UI-effects отделены от обязательных cache-effects; нет proxy-hooks |
| SSR | Request-scoped client на сервере, стабильный client в браузере |
| Обезличенность | Примеры содержат только вымышленные сущности, нет внутренних URL, путей или данных |

## Проверяемые сценарии реализации

Это критерии для проекта, который внедряет Kit, а не заявление о наличии runtime-реализации в этом репозитории.

- Одинаковые параметры дают одинаковую идентичность; изменение значимого параметра меняет ключ.
- Invalidation префикса списка затрагивает его варианты и не затрагивает detail или другой домен.
- Finite и infinite queries одного ресурса не используют одну запись кэша.
- При отсутствующем или невалидном обязательном ID конкретный detail-ключ не создаётся, используется `unavailableDetail()` и `skipToken`, transport не вызывается; после появления валидного ID запрос может выполниться.
- Технический ключ заблокированного наблюдателя не содержит данных ресурса и не попадает под префикс `details()`; `all()` охватывает обе ветки. Разные операции имеют разные технические ключи.
- Имена параметров видны в ключе; отсутствие необязательного фильтра допускается только как самостоятельный вариант запроса.
- `enabled: false` блокирует автоматический запуск в consumer, но не подменяет технический guard QO.
- Отмена query передаёт abort в transport.
- `select` меняет данные наблюдателя, сохраняя исходную форму кэша.
- Успешная мутация выполняет все заявленные cache-effects; неуспешная не запускает success invalidation.
- `meta.invalidates` работает без локального onSuccess; пустой план не инвалидирует весь кэш.
- Обязательный cache-effect завершается до завершения соответствующего success lifecycle и не зависит от размонтирования компонента.
- Динамический эффект работает с клиентом исполняющей мутации, а не с другим глобальным экземпляром.
- Оптимистический rollback, если есть, корректен при ошибках и конкурирующих записях.
- Loader и UI используют один контракт ресурса; независимые SSR requests не видят данные друг друга.

Достаточно тестировать наблюдаемое поведение и важные границы. Статический анализ может дополнительно запрещать импорты `.qk` из consumer, namespace-экспорты QO/MO и `enabled` в `.qo`.

## Частые ошибки

| Ошибка | Исправление |
| --- | --- |
| `useProduct()` только вызывает `useQuery(productDetailQO({ productId: id }))` | Использовать QO прямо в consumer |
| `productQO.detail({ productId: id })` | Экспортировать `productDetailQO({ productId: id })` отдельно |
| Consumer вызывает `invalidateQueries` после `mutate` | Перенести эффект в MO |
| `useMutation({ ...productRenameMO(), onSuccess: closeDialog })` | Передать UI-callback в конкретный `mutate` |
| `queryClient.setQueryData(productDetailQO({ productId: id }).queryKey, value)` | Выполнять доменную запись в MO через QK |
| Фабрика принимает `Partial<UseQueryOptions>` | Принимать только параметры ресурса; настройки наблюдателя добавлять в consumer |
| `enabled: Boolean(id)` внутри QO | Использовать `skipToken` и точную проверку валидности ID |
| `detail(productId: string \| undefined)` в QK | Принимать `{ productId: string }`; проверять ID в QO до вызова QK |
| `[...details(), productId]` | Сохранять параметр как `{ productId }` |
| Detail и infinite query имеют общий ключ | Развести ветки и форму кэша |
| `meta.invalidates` добавлен без MutationCache | Установить универсальный executor |
