# Внедрение и ревью

[Спецификация](SPECIFICATION.md) — источник правил. Этот документ помогает применить их в существующем или новом проекте.

## Порядок внедрения

1. Зафиксировать состав проекта, совместимую версию TanStack Query v5 и строгую проверку TypeScript. Выбрать нужные материалы из [stack/](stack/README.md).
2. Выбрать один ресурс. Зафиксировать его параметры, форму ответа, текущие ключи, consumer и мутации, влияющие на кэш.
3. Отделить transport от кэширования. Transport получает аргументы и `AbortSignal`, возвращает типизированные данные или ошибку.
4. Перенести идентичность ресурса в `.qk`, сохраняя действующие ключи при миграции. Смена ключа — отдельное изменение поведения кэша.
5. Описать чтение самостоятельными QO. Перенести технические guards в `skipToken`, оставив решения об активности у consumers.
6. Описать запись самостоятельными MO и перенести туда все связанные изменения кэша.
7. Подключить типизацию meta и универсальный invalidation executor, если MO используют `meta.invalidates`.
8. Заменить consumer-код на прямое использование options. Вынести композицию QO/MO и специфичные для сценария мапперы и бизнес-guards в Aggregation при необходимости; повторное использование в других сценариях не обязательно.
9. Проверить используемые consumers на одинаковую идентичность ресурса. Если есть SSR, проверить изоляцию requests и перенос состояния по материалу выбранного framework.

Правила применяются к новому коду и существенно изменяемым модулям. Массовая миграция не обязательна. Совместимость со старыми ключами и persisted cache оценивается до их изменения. Переход от позиционного ID к `{ productId }` меняет идентичность записи кэша: все QO и cache-effects MO одной операции переводятся согласованно; для persisted cache нужно определить миграцию или сброс старых записей.

## Вопросы для ревью

| Область | Что проверить |
| --- | --- |
| Зависимости | Consumer не импортирует QK, transport не зависит от Kit |
| Ключи | Все влияющие параметры учтены, readonly tuples, именованные объекты параметров, готовые обязательные ID, разные ветки для finite/infinite |
| QO | Отдельные экспорты, signal передан, optional-QO блокирует неготовые параметры; ready-QO получает подготовленный ввод; обе совместимы с выбранными consumers |
| Параметры | QK/QO/MO принимают один именованный объект или не имеют параметров; variables mutationFn — объект |
| Типы | Максимально используется inference; явные типы обоснованы контрактом или недостающим контекстом. Нет аннотаций возвращаемого типа QO/MO и generic-аргументов options helpers; inference сохраняется из transport и select, нет `any` или скрывающих ошибку casts |
| MO | Все cache-effects внутри MO, callbacks не перезаписаны consumer, Promise ожидается |
| Meta | Тип зарегистрирован и executor действительно установлен на используемом клиенте |
| Aggregation | Только ссылки на QO/MO и чистые функции; нет hooks, keys и side effects |
| Consumer | UI-effects отделены от обязательных cache-effects; нет proxy-hooks |
| Ошибки | Типы сохраняют error-контракт приложения; ошибки transport не превращены в успешные данные; фоновая ошибка сохраняет доступный UI |
| Восстановление | Сброс UI и состояния операции согласованы; отклонённые Promise обработаны; единый канал уведомлений и определённая retry-политика |
| SSR, если используется | [Общие принципы](SPECIFICATION.md#общие-принципы-ssr): изоляция requests, идентичность ресурса, передача данных и свежести; конкретный lifecycle выбранного framework |
| Обезличенность | Примеры содержат только вымышленные сущности, нет внутренних URL, путей или данных |

## Аудит мест потребления

Начните со сценария и его consumers: проследите использование QO/MO и чистых функций Aggregation, затем сопоставьте чтения и cache-effects с иерархией QK. Рассмотрите область каждого префикса, идентичность ресурса во всех местах использования и последствия мутации для затронутых записей. Изолированная проверка структуры QK не показывает корректность выбора префикса в MO.

Ниже — вопросы для аудита реализации, а не обязательный набор unit-тестов каждой фабрики. Необходимость поведенческих тестов определяется [критерием соответствия](SPECIFICATION.md#10-критерий-соответствия).

- Одинаковые параметры дают одинаковую идентичность; изменение значимого параметра меняет ключ.
- Invalidation префикса списка затрагивает его варианты и не затрагивает detail или другой домен.
- Finite и infinite queries одного ресурса не используют одну запись кэша.
- В optional-QO при отсутствующем или невалидном обязательном ID конкретный detail-ключ не создаётся, используется `unavailableDetail()` и `skipToken`, transport не вызывается; после появления валидного ID запрос может выполниться.
- Ready-QO исполняется с подготовленными параметрами; проверка внешнего ввода происходит до её вызова.
- Технический ключ заблокированного наблюдателя не содержит данных ресурса и не попадает под префикс `details()`; `all()` охватывает обе ветки. Разные операции имеют разные технические ключи.
- Имена параметров видны в ключе; отсутствие необязательного фильтра допускается только как самостоятельный вариант запроса.
- `enabled: false` блокирует автоматический запуск в consumer, но не подменяет технический guard QO.
- QueryFn передаёт signal в transport; реализация отмены транспорта проверяется в его собственном слое.
- `select` меняет результат consumer, сохраняя исходную форму кэша.
- Подтверждённая запись запускает заявленные success cache-effects; отказ mutationFn не запускает success invalidation.
- `meta.invalidates` работает без локального onSuccess; пустой план ничего не инвалидирует, пересекающиеся префиксы не запускают повторные refetch одной query.
- Обязательный cache-effect завершается до завершения соответствующего success lifecycle и не зависит от размонтирования компонента.
- Динамический эффект работает с клиентом исполняющей мутации, а не с другим глобальным экземпляром.
- Оптимистический rollback, если есть, корректен при ошибках и конкурирующих записях.
- Типы QO/MO сохраняют общий error-контракт приложения.
- Неуспешный фоновой refetch сохраняет данные; два observer не создают два глобальных уведомления.
- Все используемые consumers используют один контракт ресурса; при SSR независимые requests не видят данные друг друга.
- При SSR восстановленный кеш сохраняет идентичность, форму и возраст данных; payload содержит только разрешённые получателю данные.
- Если ресурс отображается в серверном и клиентском lifecycle, после мутации проверено их согласование согласно framework adapter.
- Отказ success callback после подтверждённой записи не запускает rollback этой записи или повтор команды; неизвестный результат восстанавливается согласно контракту повторяемости.
- Сценарий скрывает данные и состояния операций, которые больше ему не нужны; отключение query не считается очисткой её result.
- Отклонённые Promise обрабатываются независимо от UI-границы ошибок.

Проверки hooks, Suspense, routing и framework reset выбираются только для используемых технологий из [stack/](stack/README.md).

Содержательная последовательность cache-effects, условное обновление, optimistic update и rollback могут требовать поведенческих тестов. Чистые мапперы и бизнес-правила проверяются по их сложности; объекты со ссылками и декларативные конфиги не требуют отдельных тестов. Статический анализ может дополнительно проверять границы модулей из спецификации.

## Частые ошибки

| Ошибка | Исправление |
| --- | --- |
| Wrapper только проксирует ресурсную QO | Использовать QO прямо в consumer |
| `productQO.detail({ productId: id })` | Экспортировать `productDetailQO({ productId: id })` отдельно |
| Consumer вызывает `invalidateQueries` после `mutate` | Перенести эффект в MO |
| Consumer перезаписывает callback MO | Использовать отдельный UI-callback выполнения, сохраняя lifecycle MO |
| `queryClient.setQueryData(productDetailQO({ productId: id }).queryKey, value)` | Выполнять доменную запись в MO через QK |
| Возвращаемый тип QO/MO аннотирован или helper вызван как `queryOptions<Type>` | Следовать [правилу вывода типов фабрик](SPECIFICATION.md#2-модули-и-зависимости); типизировать входные данные и transport |
| Фабрика принимает `Partial<UseQueryOptions>` | Принимать только параметры ресурса; настройки наблюдателя добавлять в consumer |
| `enabled: Boolean(id)` внутри QO | Использовать `skipToken` и точную проверку валидности ID |
| `detail(productId: string \| undefined)` в QK | Принимать `{ productId: string }`; проверять ID в QO до вызова QK |
| `[...details(), productId]` | Сохранять параметр как `{ productId }` |
| Detail и infinite query имеют общий ключ | Развести ветки и форму кэша |
| `meta.invalidates` добавлен без MutationCache | Установить универсальный executor |
