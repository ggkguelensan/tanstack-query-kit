# Оптимизация query-подписок

Найди обоснованные границы подписок: приблизь observer к фактическому потребителю данных и сузь его `select`, сохранив поведение приложения. Глубина hook и число удалённых props сами по себе не доказывают улучшение.

## Контекст и область работы

Определи целевой React-проект, его инструкции, установленную версию `@tanstack/react-query` и область запроса: компонент, маршрут, QO или приложение. Для аудита выдай рекомендации; при запросе оптимизации или рефакторинга реализуй подтверждённые изменения в разрешённой области. Не распространяй локальный запрос на всё приложение.

Прочитай принятые проектом правила Kit. Если их нет, используй канонические [SPECIFICATION.md](https://github.com/ggkguelensan/tanstack-query-kit/blob/main/SPECIFICATION.md) (разделы 2–4, 6–8) и [React](https://github.com/ggkguelensan/tanstack-query-kit/blob/main/stack/react/README.md). При работе в checkout Kit читай эти файлы локально. Не копируй спецификацию в приложение и не превращай оптимизацию в миграцию его архитектуры. При недоступности контракта явно укажи ограничение анализа.

Перед выбором преобразований прочитай [примеры решений](references/decisions.md). Это иллюстрации, а не требования к именам и структуре приложения.

## 1. Найди точки подписки и идентичность query

Начни с поиска `useQuery`, `useSuspenseQuery`, `useInfiniteQuery`, `useSuspenseInfiniteQuery`, `useQueries`, `useSuspenseQueries` и файлов `.qo`. Поиск текста даёт кандидатов; подтверди связи через imports, symbols и исходники. Учитывай переименованные imports, namespace-вызовы, barrel exports, локальные hooks, spread options и ссылки через Aggregation. Не определяй семантику по имени функции или суффиксу файла без проверки.

Для каждой точки запиши:

- QO и место её определения; путь вызова через обёртки до компонента, в котором живёт observer.
- Прикладные параметры и источник каждого параметра: props, route, context, state, другой query.
- Идентичность по построению `queryKey`, finite/infinite-форме и фактическому QueryClient/cache. Учитывай custom hash, если он настроен. Исследовать QK в исходниках допустимо; добавлять извлечение ключа из QO в production consumer не нужно.
- Эффективные настройки после spreads и defaults: `select`, готовность параметров, `enabled`/`skipToken`, свежесть, refetch, placeholder/initial data, обработка ошибок и уведомления observer.
- Места prefetch/loaders и условия mount/unmount, влияющие на начало загрузки.

Одна QO с разными параметрами не означает одну запись кеша. Разные фабрики могут описывать один ресурс; не объединяй их без подтверждения одинаковой идентичности и формы данных. Для динамических параметров фиксируй выражение и условия совпадения, не выдумывай runtime-значения.

## 2. Восстанови дерево компонентов и поток результата

От каждой подписки проследи `data` до всех доступных потребителей в выбранной области. Учитывай `const { data: reactiveData }`, `query.data`, aliases, destructuring, props со сменой имени, spreads, context, render props, callbacks, effects, `useMemo`, helper-функции и state-копии. Граница компонента не завершает трассировку.

Отдельно проследи используемые свойства результата: статусы, ошибки, `refetch`, а для infinite — `hasNextPage`, `isFetchingNextPage`, `fetchNextPage` и обратную пагинацию. Для `useQueries` учитывай индексы/сопоставление элементов и `combine`.

Классифицируй каждый шаг:

| Роль | Признак |
| --- | --- |
| Передача | Только передаёт исходные или производные данные дальше |
| Преобразование | Выбирает поля, фильтрует, сортирует, группирует, объединяет, вычисляет агрегат |
| Потребление | Рендерит, проверяет условие, использует в handler/effect, формирует параметры query или mutation |

Для преобразования запиши входные поля, выход, зависимости от локального состояния и других queries, чистоту и предполагаемую стоимость. `data.length > 0` и извлечение ID зависимого запроса — потребление. Копирование в state может быть намеренным снимком или черновиком: не заменяй его живой подпиской без сохранения семантики.

Покажи дерево компонентов с наложенными путями данных и преобразованиями; при слиянии нескольких источников используй граф. Один компонент может иметь несколько call sites с разными параметрами и жизненным циклом. Отмечай условия рендера, повторяемые элементы, QueryClientProvider, Suspense и ErrorBoundary.

Статическое дерево — приближение runtime-дерева. Неразрешённые dynamic components, внешние функции, непрозрачные spreads и context-пути отмечай явно с последним подтверждённым местом. Не объявляй покрытие полным и не удаляй подписку, пока её потребители не установлены.

## 3. Выбери границы подписок

Для каждой query сравни сохранение текущей подписки, перенос и разделение по независимым веткам.

| Наблюдение | Кандидат на изменение |
| --- | --- |
| Один потребитель за цепочкой посредников | Перенести hook к потребителю или ближайшему содержательному контейнеру |
| Независимые ветки используют разные проекции | Создать observers той же query ближе к веткам с отдельными `select` |
| Родителю нужен агрегат, детям детали | Сохранить узкий observer родителю, дать детям собственные подписки |
| Соседним компонентам нужна одна дорогая модель | Рассмотреть общий observer в ближайшем контейнере |
| Большой список повторяемых consumers | Оценить количество observers и вычислений; не создавать hook на каждую строку автоматически |
| Переиспользуемый UI принимает готовые данные | Рассмотреть feature-контейнер, сохранив публичный интерфейс UI |

Два потребителя — основание рассмотреть разделение, не достаточное условие. Считай также стоимость передачи параметров вниз, новых связей с доменом, повторных вычислений и изменения lifecycle. Не создавай pass-through hook вокруг QO или hook, скрыто исполняющий Aggregation; следуй принятому контракту Kit.

Обоснуй эффект конкретно: какие посредники перестают читать результат query, какие поля перестают влиять на выбранный результат, какие преобразования получают отдельную ответственность. Узкий `select` не предотвращает рендеры из-за родителя, context или state; используемые статусы также могут обновлять consumer. Не обещай ускорение без измерений.

## 4. Сохрани семантику select и lifecycle

### Select

- Добавляй observer-настройки через spread исходной QO. Сохраняй именованные параметры, вывод типов и границы QK/QO/MO/Aggregation; не меняй `queryKey`, `queryFn` или cache-shape ради размещения подписки.
- Проверь существующий `select` в QO и consumer. Новый `select` после spread **заменяет**, а не дополняет старый и получает исходные cache data. Если раньше преобразование использовало результат старого selector, явно сохрани композицию чистых функций и типы.
- Переноси чистые проекции, не эффекты, мутации, проверку transport-ошибок или изменение исходного массива через `sort`/`reverse`. Данные кеша не мутируются.
- Для selector с внешними зависимостями сохрани актуальность closure; при полезной мемоизации используй стабильную функцию либо `useCallback` с полными зависимостями. Не превращай соединение нескольких queries в скрытую зависимость одного `select` от чужого кеша.
- Общая функция selector не означает общий результат вычисления для всех observers. Дорогую повторяемую работу оцени отдельно. Не добавляй глобальный memo-cache без обоснования и политики жизненного цикла.

### Загрузка и ошибки

- Сохрани готовность параметров, условия активности, поведение placeholder/initial data и смены ключа. Не заменяй `useQuery` на Suspense или наоборот как побочный эффект оптимизации. Hooks не вызываются условно или внутри цикла.
- Разделяй ранний запуск загрузки и позднюю подписку. Не удаляй полезный loader/prefetch вместе с родительским observer. Проверь холодный кеш, условные вкладки, lazy-компоненты и зависимые запросы на отложенный запуск и waterfalls.
- При Suspense сопоставь старые и новые границы ожидания, ошибки и reset, включая фоновые ошибки и порядок независимых запросов. Не меняй видимую область fallback без обоснования в рамках задачи. Для параллельности проверь существующие `useSuspenseQueries`/prefetch.
- Несколько observers могут разделять запись кеша и текущую загрузку, но новый mount устаревшей query может вызвать refetch. Проверь свежесть, refetchOnMount, polling, unmount/cancellation и provider scope. Не увеличивай staleTime и не выключай refetch только ради скрытия регрессии.

### Infinite

- Сохрани исходные `pages`/`pageParams`, QO и контракт курсоров в кеше; finite и infinite не взаимозаменяемы. Проекция `select` может иметь другую форму, если это поддерживается установленными типами и consumer; не выдавай её за изменение cache-shape.
- Проследи владельца кнопки, intersection observer или другого триггера пагинации. Дополнительный читатель не должен автоматически получать эффект загрузки страниц.
- Сохрани условия `hasNextPage`, проверки fetching, обработку ошибок, порядок страниц и взаимодействие next/previous fetch с refetch. Не размножай конкурирующие триггеры и не создавай локальные копии страниц как второй кеш.

При неоднозначной семантике используй документацию установленной версии: [render optimizations](https://tanstack.com/query/v5/docs/framework/react/guides/render-optimizations), [waterfalls](https://tanstack.com/query/v5/docs/framework/react/guides/request-waterfalls), [Suspense](https://tanstack.com/query/v5/docs/framework/react/guides/suspense), [infinite queries](https://tanstack.com/query/v5/docs/framework/react/guides/infinite-queries). Не добавляй API из более новой версии без проверки.

## 5. Результат и проверка

Для каждой рекомендации или выполненного изменения покажи:

1. QO, параметры/идентичность и исходную точку подписки со ссылками `файл:строка`.
2. Компактные деревья **до/после**: потребители, передаваемые данные, преобразования и новые `select`.
3. Решение: сохранить / перенести / разделить / недостаточно данных; объяснение пользы и существенных компромиссов.
4. Что сохраняет загрузку, статусы, ошибки и пагинацию; неизвестные связи и покрытие анализа.

При реализации сначала проверь исходные потребители, затем меняй подписки и удаляй только доказанно лишние props/преобразования. Выполни принятые проектом typecheck/lint и релевантные проверки изменённого поведения. Проверяй сценарии, затронутые изменением: холодный/тёплый кеш, смена параметров, mount/unmount, invalidation/refetch, ошибка/reset и infinite pagination. Добавляй тесты для существенных рисков, а не для проверки совпадения текста реализации.

Отдельно сообщи измеренные результаты и предположения. Если runtime-проверка недоступна, перечисли непроверенное; успешный typecheck не доказывает отсутствие waterfall или лишних запросов.
