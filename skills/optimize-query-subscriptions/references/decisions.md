# Примеры решений

Иллюстративные сценарии для выбора границ подписок. Названия компонентов и фабрик условные. Каждый сценарий предполагает проверку фактического query key, параметров и QueryClient.

## Независимые проекции одной query

До:

```text
Page — useQuery(orderListQO(params)) → orders
└─ Layout — передаёт orders
   ├─ Summary — filter(isPaid).length
   └─ OrdersSection — передаёт orders
      └─ OrdersTable — filter(isVisible).map(toRow)
```

После, если начало загрузки и UI-состояния сохранены:

```text
Page — params; прежний loader/prefetch, если он был
└─ Layout
   ├─ SummaryContainer — useQuery + selectPaidCount
   │  └─ Summary — count
   └─ OrdersSection
      └─ OrdersTableContainer — useQuery + selectVisibleRows
         └─ OrdersTable — rows
```

Оба observer используют `orderListQO(params)` с одинаковой идентичностью. `selectPaidCount` нужен только счётчику; таблица получает отдельную проекцию. Контейнер не обязателен, если сам компонент является feature-consumer. Проверить условия mount обеих веток и нового refetch; не обещать ровно один сетевой запрос.

## Родитель тоже потребляет данные

```text
Panel — query.data.length > 0 решает, показывать ли секцию
└─ Table — читает записи
```

Panel не является посредником. Возможны узкая подписка Panel на наличие записей и отдельная подписка Table либо сохранение общей подписки. Нельзя удалить родительское чтение, не сохранив условие показа и поведение при отсутствии данных.

## Существующий select не складывается с новым

Пример исходного контракта: cache data имеют вид `{ items: Order[] }`; QO содержит `select: response => response.items`; consumer вычисляет количество оплаченных заказов из полученного массива.

После `useQuery({ ...orderListQO(params), select: selectPaidCount })` функция `selectPaidCount` получит объект ответа, а не массив. Требуется сохранить эквивалент `response => selectPaidCount(selectItems(response))`, используя доступные чистые функции в принятых проектом слоях. Не обходить проблему casts и не менять форму кеша.

## Поздний mount меняет начало загрузки

```text
До:    Page — useQuery → Dialog (монтируется при открытии)
После: Page → Dialog — useQuery (загрузка только при открытии)
```

Уменьшение prop drilling здесь откладывает запрос. Если ранняя загрузка нужна, сохранить её через существующий механизм prefetch или оставить подписку. При Suspense дополнительно проверить fallback и отсутствие нового последовательного ожидания. Решение зависит от требуемого UX, а не только от расстояния до consumer.

## Два читателя infinite query

```text
Feed — useInfiniteQuery(feedQO(params))
├─ Counter — число загруженных записей
└─ List — страницы и onEndReached → fetchNextPage
```

Можно перенести подписки к Counter и List, сохранив один владеющий пагинацией List. Counter выбирает только число загруженных записей; это не общее количество на сервере. Он не получает автоматический эффект `fetchNextPage`. Проверить пересечение триггера следующей страницы с refetch и обновление обеих проекций после загрузки.

## Разделение без доказанной пользы

```text
TableContainer — expensiveNormalize(data)
└─ 1000 Row — разные поля нормализованной модели
```

1000 отдельных observers с повторным `expensiveNormalize` могут оказаться дороже общей подготовки и передачи rows. Рассмотреть стоимость вычисления, частоту изменений, виртуализацию и существующие границы рендера. Сохранение текущей подписки — допустимый результат аудита.

## Неполное покрытие

```text
Page — data → <ExternalRenderer {...makeProps(data)} />
```

Если реализация `makeProps` или внешнего renderer недоступна, отметить непрозрачную связь. Подтверждённые ветки можно анализировать отдельно; удалять исходную подписку на основании отсутствия найденных consumers нельзя.
