# TanStack Query Kit

Переносимая архитектурная спецификация слоя серверного состояния на **TanStack Query v5** и TypeScript. Kit определяет, где объявлять запросы, ключи, мутации и композицию данных, чтобы один контракт использовался в UI, предзагрузке и SSR.

Это набор соглашений для внедрения в свой проект. Отдельного runtime-пакета устанавливать не требуется. Основной контракт не предполагает UI-framework, роутер, SSR или дополнительный state manager. Конкретные интеграции раскрываются отдельно по составу проекта.

## Четыре вида модулей

| Файл | Экспорт | Отвечает за |
| --- | --- | --- |
| `product.qk.ts` | `productQK` | Иерархию ключей кэша |
| `product.qo.ts` | `productDetailQO`, `productListQO` | Контракт чтения ресурса |
| `product.mo.ts` | `productRenameMO` | Запись и весь эффект операции на кэш |
| `product-page.aggregation.ts` | `productPageAggregation` | Композицию QO/MO и доменных функций сценария |

Consumer передаёт QO/MO целиком в API выбранного адаптера. [React-каталог](stack/react/catalog.md) показывает конкретную реализацию; другие материалы выбираются через [stack/](stack/README.md).

Kit распределяет ответственность за идентичность, чтение, запись и сценарий. Consumer определяет последовательность и lifecycle; Aggregation необязательна. Контракт параметров и готовности описан в [QO](SPECIFICATION.md#4-query-options-qots).

## Как использовать

1. Принять [спецификацию](SPECIFICATION.md) как соглашение проекта.
2. Разместить модули рядом с соответствующей сущностью или feature; конкретная структура каталогов не обязательна.
3. Подключить типизацию `meta.invalidates` и универсальный `MutationCache`, если используются декларативные invalidation-планы.
4. Переносить существующий код постепенно по [критериям внедрения](ADOPTION.md).

Примеры используют вымышленные сущности. Область применения и проверенные версии указываются в соответствующем материале стека.
